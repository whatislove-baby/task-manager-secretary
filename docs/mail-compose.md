# 邮件写作与发送：本分支新增功能

上游主要完成「导入邮件 → AI 分析 → 确认待办」。本分支增加「AI 起草／润色 → 人工编辑 → 发送预览 → SMTP 发送」，用于联系队友、确认事项、根据来信提出改期等场景。AI 只生成主题和正文；收件人由用户填写或核对，发送由用户单独确认。

## 使用流程

1. 在设置中保存 AI 服务地址、模型和 Key。使用 OpenRouter 时地址为 `https://openrouter.ai/api/v1`，模型 ID 以账号实际可用的为准。手动写作不需要模型连接。
2. 点击邮件工作台顶部「写邮件」，或从已导入邮件的详情点击「根据来信写回复」。回复入口显示原邮件主题与发件人，收件人仍留空，请自行核对填写。
3. 填写「写信要求」，例如「礼貌说明原时间有课，建议改到11月22日16:00，请对方确认」，点击「AI 起草／润色」。检查草稿，再直接修改收件人、主题、正文。也可不调用 AI，手动输入或点击「复制正文」。未明确的时间不能当作已确认安排；这一步不会创建待办或改动日历。
4. 选择已配置的 IMAP 邮箱，保存 SMTP 服务器、端口和加密方式。SMTP 使用此邮箱现有的用户名和加密保存的授权码；不要在聊天、示例或交接记录中填写真实授权码。
5. 点击「预览并准备发送」，核对发件人、收件人、主题、全文及实际附件版本，再点击「确认发送这封邮件」。预览对应一份固定内容；编辑后应重新生成预览。生成或预览本身不会发信。
6. 查看发送记录。`sent` 表示 SMTP 服务器已接受；不证明邮件已送达、进入收件箱或被阅读。

当前支持单个收件人、纯文本正文与文件附件；收件人填写一个完整邮箱地址，不支持显示姓名、多个地址或非 ASCII 邮箱地址。尚无抄送、密送或定时发送。根据来信写作会使用所选本地邮件作为上下文；现有邮件库未保存可用于回复的原始 Message-ID，因此尚未设置 In-Reply-To／References 邮件头，不承诺邮件客户端将它归入原会话。程序保存本地发送记录，不自动向服务器的「已发送」文件夹追加副本；服务商可能自行保存。

## 附件与资料生成

完整步骤、样例和交接表见附件与文件处理报告（本地历史材料未随仓库发布）。从邮件详情选择“读取附件并处理”，或在“AI 对话历史”勾选“读取资料／生成文件”并添加本地 PDF、DOCX、UTF-8 TXT／Markdown；明确提交后才把所选文件文字交给模型。选择输出格式，处理后可另存文件，或点“加入邮件附件”。修改上一版时先点产物卡片的“作为本轮资料”，生成新副本，不覆盖原件；当前不支持 OCR 或保留原文档版式编辑。

写信页可以选择本地资料库中的附件；“AI 起草时参考附件内容”默认关闭。只勾选此项并起草时才发送附件文字作为模型上下文。附件最多 6 个，总大小不超过 10 MiB；准备发送时保存固定字节快照，预览列出文件名、大小和版本。修改正文或附件后必须重新预览，发送结果不确定时不能用新附件解锁旧快照。

文件源副本、提取文字与生成产物保存在应用数据目录的文件资料库，发送附件快照保存在 `mail-compose.sqlite`。它们不包含在普通待办 JSON 备份中；需要完整备份时退出应用后复制数据目录。定时邮件整理仍不自动读取附件。四个合成端到端场景使用受控模型与 SMTP；见结果（本地历史材料未随仓库发布），不能作为真实发信证明。

## 邮箱配置

QQ 或网易普通邮箱通常需要先在网页版开启 IMAP/SMTP，并生成客户端授权码。这里继续使用原有 IMAP 账号设置；SMTP 是另一条连接，读取成功并不证明发信成功。使用界面中的服务商预设或按服务商说明填写，必须使用 SSL/TLS 或 STARTTLS，程序验证证书。

QQ 当前指引为网页版右上角头像 → 设置 → 账号与安全 → 安全设置 → 开启服务 → 生成授权码；16位授权码用于第三方客户端的 IMAP／SMTP 登录。界面调整时以 [QQ 邮箱官方帮助](https://help.mail.qq.com/detail/106/985) 为准。填写的是授权码，不是 QQ 登录密码。

本功能不使用学校 Microsoft 365 的客户端 ID，也未实现 Graph 发信。已配置的 Microsoft 只读账号不会因此获得发送能力。更换 IMAP 账号或服务器后，应重新检查 SMTP 配置与授权码。主动断开邮箱会清除原凭据，再发送前需重新配置。

发送失败分为：

| 状态 | 含义与处理 |
| --- | --- |
| `prepared` | 已保存预览，尚未发送。 |
| `sending` | 本次发送正在进行，不能重复点击发起同一份发送。 |
| `sent` | 服务器明确接受。重复确认同一记录不再次发送。 |
| `failed` | 明确失败；检查配置或收件人，不自动重试。 |
| `uncertain` | 连接中断等情况导致无法确认服务器是否接受。先检查真实邮箱，避免重复发信。 |

SMTP 不提供通用的「恰好发送一次」保证。本分支防止同一发送记录的重复提交；如果用户主动创建另一份预览，仍可能发送相同内容。应用中途退出后，不会自动重发尚未确认结果的发送。

## 代码与接口

```text
MailComposePanel（编辑、预览、确认）
    ↓ window.mailCompose / Electron IPC
MailCompose（AI JSON 校验、固定预览、发送状态）
    ├─ 现有 AI 设置 → chat/completions → {subject, body}
    ├─ 本地邮件库 → 回复上下文
    ├─ 明确选中的文件 → 可选 AI 参考／固定附件快照
    ├─ 现有 IMAP 账号 → 加密凭据
    └─ Python smtplib + TLS → SMTP 服务器
```

入口为 `src/renderer/MailComposePanel.tsx`、`src/shared/mail-compose.ts`、`backend/task_backend/mail_compose.py`。主要接口为 `generate`、`prepare`、`send` 和 `listRecent`；配置通过 `getConfig`、`saveConfig` 读写。收件人和邮件头在后端校验，模型不能通过返回一个新收件人来控制发送对象。来信作为不可信资料传给模型，AI 输出仍须人工核对。

SMTP 配置和固定预览／发送记录位于 `data/mail-compose.sqlite`，正文是本地明文；授权码仍留在原 IMAP 的加密凭据中。「最近发送记录」可刷新查看持久化结果；尚未准备的编辑区内容没有自动保存，关闭窗口前请自行复制需要保留的文字。JSON 待办备份不包含此数据库，完整备份需退出应用后复制 data；备份中含邮件正文，应自行妥善保管。

## 交接与验收

保留的合成输入与预期输出在 [compose_cases.json](../examples/handover/compose_cases.json)。两个代表性场景是发起讨论和回复改期；失败场景包括模型截断与发送结果不明。先用受控 AI/SMTP 测试重跑工作流，再由队友使用自己的测试邮箱验收实际连接。

接手同学需亲自完成：

1. 运行 `npm run check`，检查新增邮件写作测试结果；不把测试桩的成功称为真实发信成功。
2. 按两个正常用例检查草稿可编辑、预览与编辑内容一致，并确认预览前没有发信。
3. 检查模型截断不会替换原有正文；同一记录重复确认不会再次发送；结果不明不会自动重试。
4. 如进行真实测试，先将收件人改为自己控制的测试邮箱，检查完整内容后在应用中确认发送；记录服务商、结果与时间，不保存授权码或私人正文。
5. 在 交接记录表（本地历史材料未随仓库发布） 如实写下接手人、观察、问题和教训。自动化结果不能代替这一步。
